# Чат Александра для Tilda → Telegram

Живой чат для senyamarketing.ru и @SenyaaMarketing_chat_bot. Node.js 24, Express 5, PostgreSQL. Без ИИ. Исходники сервера в src/, изолированный Shadow DOM виджет в public/widget.js. Демо: `/`. Клиент опрашивает сервер каждые 4 секунды, пока вкладка видима, в том числе при свёрнутом чате. Посетителю Telegram не нужен.

## Бесплатная альтернатива Railway

Подготовлено размещение на **Render Free + Neon Free**: [конфигурация и ограничения](docs/FREE-HOSTING.md), Blueprint `render.yaml`. Отдельный проект Neon уже создан: `senyamarketing-chat`, PostgreSQL 18, тариф Free. Подключение Render ещё ожидается. Публичного сервера пока нет. После простоя у бесплатного Render возможна задержка пробуждения около минуты; эта схема не обещает мгновенный ответ круглосуточно.

## 1. Локальный запуск

```sh
npm ci
cp .env.example .env
```

Нужна PostgreSQL 16+ (локальная или отдельная тестовая). Подставьте DATABASE_URL. В локальном .env используйте NODE_ENV=development, PUBLIC_URL=http://localhost:3000, TRUST_PROXY=0 и добавьте http://localhost:3000 в ALLOWED_ORIGINS. Для реального запуска укажите серверные секреты и IDs, как ниже. Не коммитьте .env.

```sh
node --env-file=.env src/server.js
```

Откройте http://localhost:3000. Миграция выполняется при старте под advisory lock. Повторный запуск безопасен. Отдельная команда миграции: `node --env-file=.env scripts/migrate.js`.

Для локального демо без секретов после `npm ci` выполните `npm run demo` и откройте http://localhost:3000. Эта команда использует временную PGlite-базу и подменённый Telegram: статус передачи здесь относится к mock API. Данные такого демо исчезают после остановки; оно предназначено только для разработки. Продакшен-запуск `npm start` всегда требует PostgreSQL и серверные переменные.

Для полностью автономной проверки без секретов и внешней базы:

```sh
npm test
npx playwright install chromium
npm run test:browser
```

Интеграционные тесты используют PGlite, настоящий PostgreSQL в WASM, включая запись на диск и повторное открытие. Это не проверка сетевого подключения к обычному PostgreSQL или инфраструктуры Railway. Telegram API подменён. Браузерный тест запускает локальный сервер и проверяет виджет на десктопе и узком экране.

## 2. Размещение на Railway

Используйте уже заполненный репозиторий https://github.com/senyaav27/-senyamarketing-chat. Файлы конфигурации размещены в корне. Не загружайте .env или серверные секреты. После снятия ограничения Railway продолжайте ниже.

1. В Railway создайте отдельный проект и добавьте PostgreSQL штатным сервисом базы. Включите доступные вашему тарифу резервные копии, проверьте восстановление и ограничьте доступ к проекту.
2. Добавьте сервис из созданного GitHub-репозитория. В корне уже лежат Dockerfile и railway.json. Docker собирает `npm ci --omit=dev`. Запуск: `node src/server.js`. Healthcheck: `/health`.
3. В Variables сервиса приложения задайте DATABASE_URL ссылкой на переменную базы, например `${{Postgres.DATABASE_URL}}`, если сервис БД называется Postgres. Используйте внутренний адрес Railway. Не отключайте проверку TLS ради внешнего подключения; для внешней базы используйте доверенный CA через стандартные настройки pg.
4. Сгенерируйте публичный HTTPS-домен сервиса в его Networking. Впишите этот origin в PUBLIC_URL без пути. Домен также добавьте в ALLOWED_ORIGINS, если будете проверять демо на самом сервере.
5. Заполните остальные переменные по таблице. После изменения Variables Railway перезапустит сервис. Убедитесь, что healthcheck зелёный и `/health` возвращает `{"ok":true}`.
6. Оставьте одну реплику на старте и отключите засыпание сервиса: очередь обрабатывается внутри процесса. Очередь использует блокировки строк и допускает несколько процессов, но нагрузочное тестирование масштабирования не выполнялось.
7. Выполните настройку Telegram webhook и проверку цепочки ниже. Только затем подключайте виджет к опубликованному сайту.

Диск приложения не используется для данных. PostgreSQL хранит переписку, заявки, ключи дедупликации и очередь. Volume приложению не нужен. Миграция идемпотентна; будущие изменения схемы оформляйте отдельными версиями с учётом обратной совместимости. Не редактируйте уже применённые миграции для разрушительных изменений.

| ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| NODE_ENV                | production                                                                                                         |
| DATABASE_URL            | Ссылка на PostgreSQL, только на сервере                                                                            |


Не вводите токен бота в чат с помощником, Tilda, URL виджета или клиентский JS. Не добавляйте HTTP access-логи с телом запросов/Authorization/полными webhook URL. Telegram API URL содержит токен; обёртка намеренно не печатает URL и текст исключений fetch.

## 3. Безопасно определить Telegram user ID и chat ID

Сторонние боты для определения ID не нужны. Выполните до установки webhook; скрипт откажется работать при существующем webhook и не удаляет его.

1. Владелец открывает именно @SenyaaMarketing_chat_bot, нажимает Start. Для группового сценария сначала добавьте своего бота в отдельную группу; ответы в общей группе проверяются одновременно по ID владельца и группы.
2. На своём компьютере в неотслеживаемом .env или в серверном окружении задайте TELEGRAM_BOT_TOKEN. Сгенерируйте временный случайный TELEGRAM_IDENTIFY_CODE, например 32 hex-символа. Не сообщайте этот код другим людям.
3. Со своего личного аккаунта отправьте боту точный код; для группы отправьте `/start@SenyaaMarketing_chat_bot ВАШ_КОД`, заменив ВАШ_КОД временным кодом. Адресованная боту команда доступна при Telegram privacy mode. Для первой версии проще использовать личный чат.
4. Запустите:

```sh
node --env-file=.env scripts/telegram.js identify
```

Скрипт читает getUpdates напрямую из Telegram по токену и выводит только IDs сообщений с вашим точным одноразовым кодом. Сверьте тип чата. Положительный user_id задайте в TELEGRAM_OWNER_ID, chat_id (может быть отрицательным) в TELEGRAM_CHAT_ID. Удалите временный код из окружения и сообщение с ним. Не путайте username и числовой ID.

Если webhook уже используется другим приложением, сначала выясните его назначение. У одного бота один webhook, установка нового переключит доставку. Скрипт identify ничего не сбрасывает. При неизвестных ID и действующем webhook потребуется безопасно получить IDs в существующей интеграции или согласованно освободить бота; не запускайте getUpdates параллельно с действующим получателем.

## 4. Настроить Telegram webhook

Команды используют только серверные переменные. Запускайте в Railway shell этого сервиса либо локально с теми же переменными через `node --env-file=.env scripts/telegram.js setup`.

```sh
npm run telegram:setup
npm run telegram:status
```

Настройка вызывает setWebhook с PUBLIC_URL + `/webhooks/telegram`, secret_token и allowed_updates=['message']. Заголовок `X-Telegram-Bot-Api-Secret-Token` проверяется сервером с timingSafeEqual. Старые обновления не удаляются. Команда status выводит только признак настройки, число ожидающих обновлений и наличие ошибки.

Откройте демо на домене Railway, добавленном в ALLOWED_ORIGINS. Напишите сообщение. Получив его в Telegram, нажмите штатную «Ответить» именно на сообщение бота с номером диалога. Отправьте текст до 2000 символов. Ответ появится на сайте через опрос, обычно при ближайшем успешном запросе. Вложения, редактирование Telegram-сообщений и ответы на заявки Tilda не отправляются посетителю; на неподдерживаемый reply разрешённый владелец получает пояснение. Сообщения посторонних пользователей игнорируются.

## 5. Подключить виджет к Tilda

Готовый фрагмент: docs/tilda-snippet.html. Замените `https://REPLACE-SERVER.up.railway.app` своим PUBLIC_URL. Секреты не нужны.

```html
<script defer src="https://REPLACE-SERVER.up.railway.app/widget.js"></script>
```

По официальной документации Tilda добавьте блок T123 («HTML-код», категория «Другое») и вставьте фрагмент. Для всех страниц можно использовать общий footer с этим блоком либо раздел HTML в HEAD сайта: «Настройки сайта → Ещё → HTML-код для вставки внутрь HEAD». Скрипт defer дожидается разбора HTML; повторное подключение защищено от второго экземпляра. Опубликуйте нужные страницы. Пользовательский код необходимо проверять на опубликованной странице, а не только в редакторе/предпросмотре.

Укажите HTTPS-домены опубликованных страниц в ALLOWED_ORIGINS, включая вариант www, если он действительно используется. Не используйте `*`. CORS не даёт доступ к диалогам: каждый API-запрос дополнительно требует 256-битный bearer secret сессии. Номер диалога не является ключом.

До публичного запуска самостоятельно укажите действительную PRIVACY_POLICY_URL. Юридические формулировки и адрес политики проект не придумывает. Ссылку можно показать в виджете; требования к согласию, составу данных и месту хранения согласуйте для своего сайта отдельно.

## 6. Подключить существующие формы Tilda

Проверено по официальной документации 17 октября 2026. Это Webhook для форм, а не Webhook API экспорта сайта.

1. Выпишите текущие получатели каждой формы, чтобы сверить после изменения. Не снимайте их флажки.
2. В «Настройки сайта → Формы → Webhook» добавьте адрес:

   `https://ВАШ-СЕРВЕР/webhooks/tilda/ЗНАЧЕНИЕ_TILDA_WEBHOOK_SECRET`

3. Не включайте передачу cookies: они не нужны и сервер их не сохраняет. Оставьте обычный формат POST с полями формы; JSON-объект также поддерживается. Не включайте корзину/массивы товаров для первой версии.
4. Сохраните получатель. В «Контенте» каждого существующего блока формы добавьте флажок нового WEBHOOK, оставив прежние получатели. Сохраните и опубликуйте страницы.
5. Впишите реальные variable names полей в TILDA_ALLOWED_FIELDS. Названия регистрозависимы; значения по умолчанию подходят только если переменные действительно Name, Phone и т.д. Не включайте пароли, cookies, платёжные поля и ненужные данные. Сервер принимает только настроенный список и ограничивает каждое поле 500 символами.
6. Отправьте тестовую заявку. В ней придут formid и tranid, документированные Tilda идентификаторы блока и заявки. После этого задайте соответствие ID формы её названию через TILDA_FORM_NAMES. Убедитесь, что все разрешённые поля дошли и прежние получатели по-прежнему работают.

Tilda требует HTTPS и ответ в течение 5 секунд; при сбое документированы ещё две попытки с интервалом в минуту. Endpoint отвечает `ok` сразу после транзакции сохранения, без ожидания Telegram. На транзитную недоступность PostgreSQL отвечает ошибкой, чтобы Tilda могла повторить запрос. Повторная заявка с тем же formid+tranid не дублируется. Подключающий тест `test=test` подтверждается без создания заявки.

В документации Tilda не указан механизм подписанного запроса или произвольного секретного заголовка. Поэтому здесь используется отдельный непредсказуемый секрет в пути endpoint, валидация, лимит частоты и дедупликация. Это bearer URL: кто его знает, может отправить заявку. Храните его как секрет; не вставляйте в публичный T123, не публикуйте в аналитике и не логируйте полный путь. При утечке смените переменную и URL в Tilda. Нельзя достоверно проверить происхождение из Tilda только по Referer/Origin. Их сервер не использует для авторизации и не сохраняет чувствительный URL.

## 7. Проверка перед переключением с Jivo

Проверяйте сначала на отдельной опубликованной странице, где Jivo не мешает новой кнопке.

1. Обычный браузер и приватное окно: два разных диалога. Напишите разный текст, ответьте на каждое сообщение в Telegram; убедитесь, что ответы не смешиваются.
2. Проверьте быстрые кнопки, свободный ввод без выбора, имя, один контакт и пропуск. Пришлите текст `<img src=x onerror=alert(1)>`: он должен отображаться текстом.
3. Свёрните виджет, ответьте из Telegram: появится счётчик. Раскройте: счётчик погаснет. Закройте страницу и вернитесь в том же браузере: история сохранится при доступном localStorage.
4. Наберите черновик и перезагрузите. Отключите сеть, отправьте сообщение, восстановите сеть и нажмите «Повторить»: текст не теряется и не дублируется. Ошибки очереди показываются как «Сохранено. Доставка повторяется», а не как фактическая доставка.
5. В тестовой группе попросите другого пользователя ответить: сайт не должен получить ответ. В продакшене не добавляйте лишних участников в чат владельца.
6. Проверьте iOS Safari и Android Chrome с экранной клавиатурой, safe area, Escape и Tab на компьютере. Эмуляция viewport не заменяет физическую клавиатуру мобильного устройства.
7. Перезапустите сервис Railway, проверьте историю и очередь. Проверьте getWebhookInfo. Не ломайте Telegram токен в действующем сервисе ради теста; сбой API воспроизведён локальными тестами.
8. Отправьте каждую действующую форму Tilda и проверьте нового и всех прежних получателей.

Только после подтверждения полной цепочки удалите/отключите реальный источник кода Jivo: это может быть вставленный script, общий footer, HEAD сайта или внешняя интеграция. Сначала сохраните исходный фрагмент для отката. Найдите его в настройках именно вашего сайта, не предполагайте название конкретного поля Jivo. Перепубликуйте страницы, очистите кеш, проверьте исчезновение старой кнопки и работу новой. При проблеме верните прежний код и временно уберите новый snippet. Этот проект Jivo не отключает.

## 8. Хранение, эксплуатация и ограничения

Сессия: криптографически случайные 32 байта, хранятся в localStorage домена сайта. На сервере хранится SHA-256. Любой код на том же домене потенциально имеет доступ к localStorage, поэтому защита сайта от XSS и контроль сторонних скриптов обязательны. Очистка данных браузера теряет доступ к прежней сессии; другой браузер/домен (www) создаёт отдельную историю. При запрете хранилища показывается предупреждение, возврат между посещениями не гарантируется.

Сообщение + outbox сохраняются одной транзакцией. Клиентские UUID/случайные ключи и Telegram update_id уникальны в БД. Повторные webhook не создают сообщения повторно. Telegram API не предоставляет idempotency key для sendMessage: при обрыве сети после фактического приёма Telegram, но до сохранения подтверждения, редкий дубль уведомления владельцу возможен. Потеря подтверждения транзакции имеет то же ограничение. Очередь обеспечивает at-least-once доставку, а не недостижимое обещание exactly-once внешнего вызова. Текст посетителя в PostgreSQL при этом остаётся единственным. На Telegram-уведомления с неподтверждённым message_id нельзя гарантировать связанный ответ; отвечайте на подтверждённое уведомление.

Повторы экспоненциальные, до часа между попытками, с учётом retry_after Telegram. Число попыток не ограничено, пока обращение не удалено сроком хранения. Порядок доставки при сбоях может отличаться от истории сайта; все уведомления содержат номер диалога. Очистка раз в час удаляет диалоги старше RETENTION_DAYS с последней активности и связанные сообщения, очередь и Telegram-связи; заявки удаляются с момента создания. Новые ответы продлевают хранение диалога. Данные резервных копий, Telegram и уже отправленные уведомления эта очистка не удаляет: настройте их сроки отдельно.

Контроль очереди, без вывода персональных данных:

```sql
SELECT count(*) AS pending, min(created_at) AS oldest FROM outbox WHERE sent_at IS NULL;
SELECT count(*) AS retrying FROM outbox WHERE sent_at IS NULL AND attempts > 0;
```

Настройте внешний мониторинг `/health` и очереди. `/health` проверяет БД, но не доступность Telegram. Логи содержат только общие коды ошибок. PostgreSQL должен быть закрыт от публичного доступа либо защищён сетевыми правилами и TLS. HTTP body до 24 KB, сообщение до 2000 символов. Лимиты хранятся в БД: создание сессий 120/час/IP, отправка 20/мин/сессия и 60/мин/IP, чтение 100/мин/сессия, контакты 8/мин, формы 100/мин/IP. TRUST_PROXY должен соответствовать доверенной цепочке прокси; неверное значение ослабляет IP-лимит. CORS не защищает публичный endpoint создания сессии от произвольного внешнего клиента. При большом спаме добавьте edge-защиту или CAPTCHA по необходимости.
